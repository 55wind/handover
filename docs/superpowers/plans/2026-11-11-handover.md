# Handover Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A hosted Next.js app where a family files one notice and an LLM agent inventories, plans and settles a deceased person's payments on the PayPal sandbox, bounded by code-enforced merchant rules.

**Architecture:** One Next.js process with in-memory state. The agent (OpenAI-compatible tool loop) talks to per-merchant desks; each desk is guard + backend. The backend is the PayPal Agent Toolkit plus a few REST calls, or an in-memory fake for development and tests.

**Tech Stack:** Next.js 16 (App Router, TypeScript, Node runtime), React 19, `openai` 4.86.1, `@paypal/agent-toolkit` 1.11.0, `ag-grid-community` + `ag-grid-react`, `tsx` for `node:test`. No database, no CSS framework unless the design skill calls for one.

**Spec:** `docs/superpowers/specs/2026-11-11-handover-design.md` (read it first; this plan does not repeat it).

## Global Constraints

- Never present simulated money movement as real. `PAYPAL_FAKE=1` is for development and tests only and shows a permanent banner.
- The model never does arithmetic on money and never decides ownership. Code does both.
- Money is a decimal string (`"17.99"`), currency `USD`; do math in integer cents.
- Dates are `YYYY-MM-DD` strings; period `end` is exclusive.
- English UI and docs. Fictional names only: Daniel Reyes, Maria Reyes, Lumen Stream, Ironwood Gym, Harbor Light Food Bank.
- Ponytail rules: the least code that works, no speculative abstractions, no new dependency for what a few lines do, one runnable check per non-trivial piece of logic.
- Windows machine. Never open a console window: no `powershell`, `cmd`, `start`, `explorer` from Bash, no PowerShell tool. Long-running commands only through the Bash tool's `run_in_background`. Stop any dev server you start.
- Subagents do not run `git add`, `git commit` or any other git write. The orchestrator commits.
- Each task owns its listed files. Do not edit files owned by another task; report what you need changed instead.
- Read parameter names for toolkit tools from the installed package (`new PayPalAgentToolkit(...).getTools()`), never from memory.

## Review Focus

1. A refund request larger than the computed refundable amount, or a second refund on the same capture: must be denied by the guard, not sent to PayPal. (Task 2 tests.)
2. A tool call targeting an id that belongs to another customer (the decoy): denied. (Task 2 tests.)
3. A date of death on a period boundary (equal to `start`, equal to `end`): refund is 100% and 0% respectively, no off-by-one. (Task 2 tests.)
4. The model stops early and leaves approved rows without an outcome: rows are re-prompted, then marked "not completed", never shown as done. (Task 4, e2e assertion.)
5. PayPal returns an error mid-execution (already cancelled, refund rejected): the row ends `blocked` with PayPal's message; other rows continue. (Task 3 fake supports injected failure; Task 4 e2e assertion.)

```ts
// lib/types.ts
export type MerchantSlug = 'lumen' | 'ironwood' | 'harborlight';
export type Tier = 'filed' | 'verified';
export type Phase = 'intake' | 'plan' | 'pause' | 'resume' | 'execute';
export type CaseStatus = 'notice' | 'planning' | 'review' | 'executing' | 'done';
export type ItemKind = 'subscription' | 'charge' | 'invoice';
export type Action = 'close' | 'take_over' | 'pause' | 'refund' | 'leave' | 'waive' | 'pay_from_estate';
export const ACTIONS_BY_KIND: Record<ItemKind, Action[]> = {
  subscription: ['close', 'take_over', 'pause'],
  charge: ['refund', 'leave'],
  invoice: ['waive', 'pay_from_estate'],
};

export interface Policy {
  prorataCurrentPeriod: boolean;      // refund the unused share of a period containing the date of death
  waiveUndeliveredInvoices: boolean;
  allowTakeOver: boolean;
  summary: string;                    // plain-language text shown to the agent and in the UI
}
export interface Merchant { slug: MerchantSlug; name: string; blurb: string; policy: Policy }

export interface Period { start: string; end: string }           // YYYY-MM-DD, end exclusive
export interface Charge { captureId: string; orderId?: string; amount: string; description: string; period: Period }
export interface RecordItem {
  id: string;                         // merchant-local, e.g. "lumen-1"; unique across the app per seeded run
  kind: ItemKind; label: string;
  paypalId: string;                   // subscription id | capture id | invoice id
  planId?: string;                    // subscriptions: needed for take-over
  amount: string; cadence?: 'month' | 'year';
  charges: Charge[];                  // subscription: period charges the merchant recorded; charge: one entry; invoice: none
}
export interface CustomerRecord { customerId: string; fullName: string; email: string; items: RecordItem[] }

export interface RefundLine { captureId: string; amount: string }
export interface Decision { action: Action; refunds: RefundLine[] }
export interface Outcome {
  state: 'done' | 'waiting' | 'blocked' | 'failed' | 'not_completed';
  refs: Record<string, string>;       // e.g. { refundId, newSubscriptionId }
  verified: boolean; note: string; link?: string;
}
export interface Item {
  id: string; merchant: MerchantSlug; kind: ItemKind; label: string;
  paypalId: string; planId?: string; liveStatus: string; amount: string; cadence?: 'month' | 'year';
  charges: (Charge & { refundable: string })[];       // refundable computed by code
  proposed?: Decision & { reason: string; question?: string };
  decided?: Decision;
  outcome?: Outcome;
}
export interface Event {
  ts: string;
  actor: 'agent' | `desk:${MerchantSlug}` | 'guard' | 'family' | 'system';
  type: 'note' | 'tool' | 'denied' | 'plan' | 'outcome' | 'status' | 'error';
  summary: string; detail?: unknown;
}
export interface Case {
  id: string; createdAt: string; demo: boolean;
  tier: Tier; status: CaseStatus; running: Phase | null;
  representative: { name: string; relation: string; email: string };
  deceased: { fullName: string; emails: string[]; dateOfDeath: string };
  wishes: string; language: string;
  document: { dataUrl?: string; text?: string; extracted?: { fullName?: string; dateOfDeath?: string; kind?: string }; mismatches: string[] };
  items: Item[]; notes: string[];     // notes: agent remarks for the family, e.g. an excluded near match
  approvedAt?: string; statement?: string;
  events: Event[];
}
export interface LedgerEntry { ts: string; caseId: string; tool: string; target: string; ok: boolean; denied: boolean; summary: string; refs: Record<string, string> }

export interface ToolDef { name: string; description: string; parameters: Record<string, unknown>; write: boolean }
export type ToolResult = { ok: true; data: unknown } | { ok: false; denied: boolean; error: string };
export interface Desk { slug: MerchantSlug; listTools(phase: Phase): ToolDef[]; callTool(name: string, args: Record<string, unknown>, caseId: string): Promise<ToolResult> }

export interface Backend {
  exec(tool: string, args: Record<string, unknown>, requestId?: string): Promise<unknown>;   // throws Error(message from PayPal)
  seedSubscription(o: { label: string; price: string; payerName: string; payerEmail: string }): Promise<{ paypalId: string; planId: string } | null>;
  seedCharge(o: { label: string; amount: string; payerName: string; payerEmail: string }): Promise<{ captureId: string; orderId: string } | null>;
  seedInvoice(o: { label: string; amount: string; recipientName: string; recipientEmail: string }): Promise<{ invoiceId: string } | null>;
}
```

`null` from a seed function means the sandbox cannot do it; the item is left out.

### Task 2: Guard, refund math, matching, plan validation

**Files:** Create `lib/guard.ts`, `lib/guard.test.ts`.

**Interfaces (produces):**

```ts
export function toCents(s: string): number; export function fromCents(n: number): string;
export function refundableCents(charge: Charge, dateOfDeath: string, policy: Policy, alreadyRefundedCents: number): number;
export function matchCustomers(records: CustomerRecord[], deceased: Case['deceased']): { owned: CustomerRecord[]; nearMatches: { record: CustomerRecord; reason: string }[] };
export function buildItems(merchant: Merchant, owned: CustomerRecord[], dateOfDeath: string, refunded: Map<string, number>): Item[];   // liveStatus 'unknown'
export interface PlanRow { item_id: string; action: Action; refund_capture_ids: string[]; reason: string; question?: string }
export function validatePlan(rows: PlanRow[], items: Item[], merchants: Record<MerchantSlug, Merchant>): { decisions: Map<string, Decision>; errors: string[] };
export interface GuardInput { tool: string; targetId: string; amountCents?: number; c: Case; item?: Item; merchant: Merchant; done: Set<string> }
export function guard(i: GuardInput): { allow: true } | { allow: false; reason: string };
```

Rules:

- `refundableCents`: period starts after the date of death: full amount. Period contains the date of death (`start <= dod < end`) and `policy.prorataCurrentPeriod`: `floor(amount * days(dod, end) / days(start, end))`. Otherwise 0. Subtract `alreadyRefundedCents`, floor at 0.
- `matchCustomers`: owned = email equals one of `deceased.emails` (trim, lowercase). Near match = not owned and shares the family name (last token, case-insensitive); reason names what differs.
- `validatePlan`: unknown `item_id`, action not in `ACTIONS_BY_KIND[kind]`, `take_over` where `!allowTakeOver`, `waive` where `!waiveUndeliveredInvoices`, or a refund capture id that is not on the item or has `refundable` of `"0.00"` are errors. Refund amounts in the returned decisions are always the code-computed `refundable`, whatever the model said.
- `guard`: no `item` (target id not owned by this case): deny "not this customer's". `suspend_subscription`, `activate_subscription`, `cancel_invoice_auto_reminder`, `generate_invoice_qr_code`: allowed in any tier when the item exists. Everything else needs `c.tier === 'verified'` and `c.approvedAt`, and must fit `item.decided`: `cancel_subscription` needs `close`; `create_subscription` needs `take_over`; `cancel_sent_invoice` needs `waive`; `create_refund` needs a matching `decided.refunds` line with `amountCents <=` that line. Key `tool:targetId` already in `done`: deny "already done".

- [ ] Write `lib/guard.test.ts` first with at least: full refund when `dod < start`; `dod === start` gives full; `dod === end` gives 0; pro-rata `120.00` over a 365-day period with 110 days left gives `36.16`; pro-rata off when policy flag is false; already-refunded subtraction; decoy is a near match and not owned; `validatePlan` replaces a model-supplied amount; every deny branch of `guard` listed above; a second identical call is denied.
- [ ] Run `npm test`, see failures, implement, run until green.

Tools a desk lists (names are the toolkit's where it has them):

- Read, all phases except intake: `find_customer_records` (args: none; uses the case; returns owned records with code-computed `refundable` per charge, plus near matches with reasons), `get_policy`, `show_subscription_details`, `get_invoice`, `get_order`, `get_refund`.
- Write: `pause` phase: `suspend_subscription`. `resume` phase: `activate_subscription`. `execute` phase: `suspend_subscription`, `cancel_subscription`, `create_refund`, `cancel_invoice_auto_reminder`, `cancel_sent_invoice`, `create_subscription`, `generate_invoice_qr_code`.

`callTool`: find the item by `targetOf`; for write tools run `guard`; on deny emit a `denied` event and return `{ok:false, denied:true}`; otherwise `backend.exec` with request id `sha256(caseId|itemId|tool)` hex prefix; on success add `tool:targetId` to the case's done set, update `store.refunded` for refunds, append a ledger entry, emit a `tool` event with a one-line plain summary; on a thrown error return `{ok:false, denied:false, error}` and log it to the ledger.

Real backend: OAuth client-credentials token cached per slot until expiry; `exec` routes toolkit tool names to `toolkit.handleToolCall` (parse the JSON string it returns; treat an error payload as a throw) and the two custom tools to `fetch`. Seeding per spec section 9: card-funded subscription, else `null`; card-funded order capture for every period charge; invoice create and send with a reminder. Use PayPal sandbox test card `4111111111111111`, any future expiry, CVV `123`, US billing address. Sandbox base URL `https://api-m.sandbox.paypal.com`.

Fake backend: per-slot in-memory objects with realistic ids, the same tool names, PayPal-shaped responses for the fields the code reads (`status`, `id`, `amount.value`, approval `links`). `failNext(tool, message)` test hook for Review Focus 5.

### Task 4: Agent, routes, end-to-end script (orchestrator)

**Files:** Create `lib/agent.ts`, `app/api/demo/route.ts`, `app/api/cases/[id]/route.ts`, `app/api/cases/[id]/run/route.ts`, `app/api/cases/[id]/events/route.ts`, `app/api/merchants/[slug]/route.ts`, `scripts/e2e.ts`.

**Interfaces (produces, consumed by Task 5):**

- `export async function runPhase(caseId: string, phase: Phase): Promise<void>` in `lib/agent.ts`.
- `POST /api/demo` -> `201 {caseId}`; `429 {error}` over the daily cap; `503 {error}` when PayPal is not configured.
- `GET /api/cases/:id` -> `Case` (document `dataUrl` omitted).
- `PATCH /api/cases/:id` body any of `{ notice: {fullName, emails, dateOfDeath, representative, wishes, documentDataUrl, documentText} }`, `{ decisions: [{itemId, action, refundCaptureIds}] }`, `{ approve: true }` -> updated `Case`; `400 {error}` with the validation message.
- `POST /api/cases/:id/run` body `{phase}` -> `202`; `409` when a run is active. `intake` chains into `plan` when the result is `verified`.
- `GET /api/cases/:id/events` -> SSE; each message is `{event: Event, case: Case}`; first message replays state as `{case}`.
- `GET /api/merchants/:slug` -> `{merchant: Merchant, ledger: LedgerEntry[], fake: boolean, sharedSlot: boolean}`.

Agent loop: chat completions, tools = each desk's `listTools(phase)` prefixed `slug__`, plus local tools `submit_plan` (plan), `record_outcome` and `finish` (pause, resume, execute). `runPhase` takes an optional model client so the e2e script can pass a scripted stand-in when no LLM key is set. Parallel tool calls run concurrently. Max 40 model turns per phase. Assistant text becomes a `note` event. `record_outcome` triggers `verifyOutcome`. After the loop, rows without an outcome are re-prompted twice, then set to `not_completed`.

- [ ] Implement, then `PAYPAL_FAKE=1 npm run e2e`: seed, intake, plan (assert five items, every item has `proposed`), approve, execute, then assert: Lumen and Harbor Light rows `waiting` with a link and the old subscription suspended; Ironwood membership cancelled; locker refund equals the code-computed amount; invoice cancelled; every `done` row is `verified`; no ledger entry shows a refund above its bound. A second run with `failNext('create_refund', ...)` ends with that row `blocked` and the rest finished.
